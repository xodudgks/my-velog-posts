<h2 id="2-pm의-시선-일정-관리를-넘어-개발팀과-완벽하게-소통하는-법">2. PM의 시선: 일정 관리를 넘어, 개발팀과 완벽하게 소통하는 법</h2>
<h3 id="제휴-서비스-assu-프로젝트-팀-합류">제휴 서비스 A:SSU 프로젝트 팀 합류</h3>
<p>그렇게 1, 2월을 공부하는데 어쩌다보니 A:SSU라는 프로젝트 팀에 PM으로 합류하게 되었다. 대부분 숭실대학교 컴퓨터학부, 글로벌미디어학부 선배들로 구성된 팀이라서 솔직히 많이 쫄았었다...</p>
<p>A:SSU는 숭실대학교의 제휴 사업을 학생들이 조금 더 편하게 관리하고 혜택을 찾을 수 있도록 도와주는 서비스이다. 현재 Kotlin으로 작업해서 안드로이드만 출시를 한 상태이고 2학기에 React Native로 마이그레이션해서 iOS까지 출시할 예정이다.</p>
<h3 id="pm의-소통-능력에-대한-고찰">PM의 소통 능력에 대한 고찰</h3>
<p>A:SSU 팀에 합류하고 가장 어려웠던 부분은 바로 소통과 일정 체크였다. 사실 이전까지 PM을 하면 항상 서비스를 기획하는 활동만 했지 실제 서비스를 운영하는 프로젝트에서 이렇게까지 일정 조율에 신경을 써본건 처음이었다. 여기서 깨달은 것은 <strong>&quot;비개발자 팀원과 개발자 팀원의 니즈가 생각보다 많이 다르다&quot;</strong>이다. 언제까지 어떤 기능을 만들지, 디자인을 언제까지 마감하고 API는 어느 시점에 만들지 등을 하나하나 생각해보다 보니 고려할 요소가 생각보다 너무 많았었다. 
<img alt="" src="https://velog.velcdn.com/images/xodud_05/post/83f30ef2-a526-4089-be59-e35b9e697af1/image.png" /> (정기회의 회의록인데 일정 관리와 소통의 중요성을 회의할 때마다 깨닫게 되었다...)</p>
<h3 id="안드로이드-스튜디오를-활용한-첫-qa">안드로이드 스튜디오를 활용한 첫 QA</h3>
<p><img alt="" src="https://velog.velcdn.com/images/xodud_05/post/36119eb1-1183-45e7-adf4-02fe58d6d5a8/image.png" />

<h2 id="3-본격적인-개발의-시작-summit-webpage">3. 본격적인 개발의 시작 (SUMMIT WebPage)</h2>
<h3 id="나만의-개발-연습장-만들기">나만의 개발 연습장 만들기</h3>
<p>프로젝트를 하면서 항상 새로운 것을 배우면서 만족을 하고 있었지만 아쉬웠던 점은 <strong>내가 직접 개발을 하는 요소가 적었다</strong>는 것이었다. 그래서 정말 나만의 개발 연습장을 만들고 <strong>TypeScript</strong>를 시작으로 <strong>Cursor</strong>를 본격적으로 써보기 위해 내가 현재 임원진을 하고 있는 밴드 동아리의 웹사이트를 만들기 시작했다.</p>
<h3 id="뭐부터-만들지">뭐부터 만들지?</h3>
<p>사실 임원진 중에 백엔드와 디자인이 한 명씩 있었지만 재학생이라서 시험 기간도 있고 그래서 많은 시간을 투자하긴 어려운 상황이었다. 그치만 그대로 시간을 보내기는 아쉬워서 작년 겨울 공연 자료를 바탕으로 정기공연 랜딩 페이지를 만들어보았다. 아무래도 IT대 X AI대 연합 밴드 소모임에 맞게 공연도 전용 웹페이지를 만들면 멋있지 않을까 해서 만들게 되었다.</p>
<h3 id="피그마-mcp-활용-시작-talk-to-figma">피그마 MCP 활용 시작 (Talk to Figma)</h3>
<p>사실 하나하나 직접 UI를 만들고 프론트 작업을 하기에는 너무나 작업량이 많은 것 같아서 피그마 MCP를 활용해서 개발을 시작해보았다. </p>
<pre><code>powershell -c &quot;irm bun.sh/install.ps1 | iex&quot;</code></pre><p>Talk to Figma 플러그인을 설치하고 자바스크립트 실행 도구인 Bunx를 설치해준다. </p>
<pre><code>bunx cursor-talk-to-figma-socket</code></pre><p>Figma와 Cursor가 실시간으로 통신을 주고 받는 서버인 WebSocket 서버를 열고 Talk to Figma MCP를 플러그인을 활용해서 연결하면 채널명이 나오고 Cursor에 연동이 되었다.

<h3 id="바이브-코딩과-프론트엔드-작업의-시작">바이브 코딩과 프론트엔드 작업의 시작</h3>
<p><img alt="" src="https://velog.velcdn.com/images/xodud_05/post/2899e029-b82c-4056-a034-110bd8817eed/image.png" />
본격적으로 Cursor AI를 활용해서 공연 랜딩 페이지를 만들어보았다. 먼저 모바일로 피그마에 디자인을 하고 MCP를 활용해서 구현을 한 뒤 Tailwind CSS를 통해 반응형을 적용해서 웹까지 확장을 하였다.

<h3 id="github-process-완전-정복기">GitHub Process 완전 정복기</h3>
<p>단순히 개발을 하는 것에서 끝나지 않고 GitHub에 저장하는 법도 익히기 시작했다. 사실 피그마, GitHub는 IT대 전공이라면 기본 소양인데 너무 늦게 시작한 것 같기도 하다...ㅎ </p>
<h4 id="새로운-작업을-시작할-때">새로운 작업을 시작할 때</h4>
<pre><code>git checkout main

git pull origin main

git checkout -b 브랜치명

git push -u origin 브랜치명</code></pre><h4 id="작업-중간에-저장하고-백업할-때-잔디-심기">작업 중간에 저장하고 백업할 때 (잔디 심기)</h4>
<pre><code>git add .

git commit -m &quot;feat: 헤더 레이아웃 완성&quot;

git push origin 브랜치명</code></pre><p>이렇게 터미널에 연결해서 GitHub 저장소에 코드를 보관하는 아주 기초적인 방법도 배우기 시작했다. 또한 브랜치를 팔 때 <strong>feat/</strong>, <strong>fix/</strong>, <strong>refactor/</strong>, <strong>hotfix</strong>, <strong>wip./</strong> 등 <strong>깃허브 브랜치 컨벤션</strong> 종류도 공부하면서 브랜치 네이밍에 대해서도 익숙해지기 시작했다.
<img alt="" src="https://velog.velcdn.com/images/xodud_05/post/6d2e823d-fe54-47ae-9353-229fbbfa0e22/image.png" /></p>
<h2 id="4-2분기-목표">4. 2분기 목표</h2>
<h3 id="ai를-비서처럼-쓰는-개발자로-탈바꿈하기">AI를 비서처럼 쓰는 개발자로 탈바꿈하기</h3>
<p>일단 드디어 개발을 제대로 시작했다는 점에서 어느 정도 나에게 스스로 칭찬을 하고 싶다. 하지만 여전히 React까지밖에 제대로 쓸줄 모르는 평범한 프론트엔드 개발자이기에 갈길은 여전히 멀다. 또한 Cursor와 피그마 MCP로만 계속 AI에게 개발을 맡기면 내가 개발하는 것이 아니라 AI가 개발하는 형태가 되버릴 수 있으니 앞으로 개발을 하며 폴더 구조를 이해하고 TypeScript의 타입들을 하나씩 정리하면서 구조를 이해보려고 한다.</p>
<h3 id="나만의-결과물-완성하기">나만의 결과물 완성하기</h3>
<p>일단 6월 25일, 26일이 정기공연이기에 그 전까지 정기공연 포스터 디자인이 나오면 랜딩 페이지를 완성시켜볼 예정이다. 동아리 회원들에게 공개해보고 사용자도 받아보면서 피드백도 받고 <strong>Vercel</strong>에 배포까지 해볼 계획이다.</p>
<h3 id="로그를-볼-줄-아는-개발자">로그를 볼 줄 아는 개발자</h3>
<p>아직까지는 프론트 구조에 대해 빠삭한 편이 아니고 특히 에러가 터졌을 때 현재는 에러를 복사해서 AI에게 맡기고 있는 중이다. 그치만 앞으로는 로그를 직접 보고 어떤 부분이 문제인지 스스로 알아내는 지구력을 길러야겠다는 생각이 많이 들고 있다. 앞으로 삽질 개발 일기도 써보면서 실력을 늘려봐야겠다. ㅎㅎ</p>
